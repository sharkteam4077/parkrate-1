# ПаркРайт

## Версия 1.3.1 — безопасная первичная инициализация базы

При первом запуске новая команда `npm start` проверяет служебную отметку в отдельной схеме PostgreSQL `hr_manager_meta`. Если приложение запускается впервые, она один раз пересоздаёт схему `public`, применяет Prisma-схему и запускает seed. После успешной инициализации сохраняется отметка. При последующих деплоях выполняется обычный `prisma db push` без сброса данных.

**Важно:** первый запуск версии 1.3.1 удалит все таблицы и данные в схеме `public` указанной базы PostgreSQL. Используй отдельную базу для ПаркРайт. Другие схемы PostgreSQL не затрагиваются. Не удаляй схему `hr_manager_meta`: в ней хранится отметка, предотвращающая повторный сброс при следующих деплоях.

Для Railway команда запуска задаётся автоматически через `railway.json` как `npm start`. Переменные `DATABASE_URL`, `ADMIN_USERNAME`, `ADMIN_PASSWORD` и `SESSION_SECRET` должны быть заданы в Variables.

 — версия 1.3.0

Тёмное русскоязычное веб-приложение для управления персоналом предприятия с несколькими филиалами. Стек: React, Vite, Express, Prisma, PostgreSQL. Подготовлено для размещения на Railway.

## Что уже работает

- Обзор предприятия: сотрудники, филиалы, количество смен и сумма начислений за текущий месяц.
- Создание филиалов.
- Создание карточек сотрудников с ФИО, телефоном, должностью, филиалом и датой трудоустройства.
- Справочник типов смен.
- Индивидуальная стоимость каждого типа смены для каждого сотрудника.
- Ручная регистрация смен руководителем, с датой и необязательным временем начала/окончания.
- Сохранение ставки в записи смены: последующее изменение тарифа не меняет прошлые начисления.
- Свод начислений по сотрудникам.
- Адаптивный интерфейс для компьютеров и телефонов.
- Отдельный личный кабинет сотрудника по адресу `/employee`.
- Индивидуальные логин и пароль для каждого сотрудника; пароли хранятся только в виде хеша scrypt.
- В кабинете сотрудник видит только свою кадровую информацию, свои смены и начисления. Разделённые HttpOnly-сессии руководителя и сотрудника.

## Фото и видео в отчётах сотрудников

Новые вложения отчётов загружаются напрямую в Cloudinary по краткоживущим подписям, которые выдаёт сервер. `CLOUDINARY_API_SECRET` не передаётся в браузер. В Railway Variables задайте:

- `CLOUDINARY_CLOUD_NAME`
- `CLOUDINARY_API_KEY`
- `CLOUDINARY_API_SECRET`

Переменные Backblaze B2 можно пока оставить: они нужны только для просмотра вложений в старых отчётах, которые уже сохранены в B2. Новые загрузки в B2 не отправляются. Перенос старых объектов из B2 в Cloudinary — отдельная миграция; эта версия сохраняет совместимость со старыми отчётами.

## Локальный запуск

Требуется Node.js 20+ и PostgreSQL.

```bash
npm install
```

Создайте `.env` на основе `.env.example` и укажите `DATABASE_URL`.

```bash
npm run db:push
npm run db:seed
npm run dev
```

Vite откроет интерфейс на `http://localhost:5173`, API работает на `http://localhost:3001`.

## Размещение на Railway

1. Создайте новый проект в Railway.
2. Добавьте PostgreSQL из каталога Railway.
3. Подключите GitHub-репозиторий с этим проектом как отдельный сервис.
4. В переменных сервиса приложения добавьте `DATABASE_URL`, используя значение из PostgreSQL-сервиса (обычно `DATABASE_URL` через Reference).
5. В `railway.json` уже настроены сборка `npm run build` и запуск с применением Prisma-схемы и добавлением стартовых данных.
6. Сгенерируйте публичный домен в настройках сервиса.

При первом запуске создаются демонстрационные записи: главный филиал, дневная и ночная смены, демонстрационный сотрудник и тестовые ставки. Их можно удалить из интерфейса базы данных или оставить для проверки.

## Вход и защита административной панели

- При открытии сайта руководитель увидит форму входа.
- Логин и пароль задаются через `ADMIN_USERNAME` и `ADMIN_PASSWORD` в Railway Variables. В исходном коде и базе данных пароль не хранится.
- После успешного входа сервер выдаёт подписанную HttpOnly-cookie сессии сроком на 8 часов. В production cookie имеет флаг Secure и SameSite=Strict.
- Все административные API закрыты серверной проверкой сессии. Без входа нельзя просматривать сотрудников, филиалы, смены, начисления, анкеты и приглашения или изменять их.
- Публичными оставлены только API проверки приглашения и отправки анкеты сотрудником.
- После 8 неверных попыток входа с одного IP ввод блокируется на 15 минут.
- Кнопка «Выйти» завершает сессию в браузере.

Это базовая защита одного главного руководителя, а не система нескольких администраторов с разными ролями. Сессия действует до 8 часов; смена `SESSION_SECRET` отзывает все ранее выданные сессии. Для публичного использования также настройте резервное копирование PostgreSQL и отдельную политику хранения персональных данных.

Также текущий финансовый раздел — управленческий учёт начислений по сменам, а не расчёт налогов или официальная бухгалтерская зарплатная ведомость.

## Личный кабинет сотрудника (версия 1.3.0)

1. Руководитель входит в административную панель и открывает раздел «Сотрудники».
2. Напротив нужного сотрудника нажимает «Выдать доступ».
3. Задаёт логин и временный пароль (не менее 8 символов), сохраняет и передаёт эти данные сотруднику безопасным способом.
4. Сотрудник открывает `https://ваш-домен/employee` и входит по выданным данным.
5. В личном кабинете сотрудник видит свои ФИО, должность, филиал, телефон, дату трудоустройства, список собственных смен и начисления.
6. Для сброса пароля руководитель снова открывает «Настроить доступ» и задаёт новый пароль. Чтобы отключить доступ, удалите логин/пароль сотрудника через API `DELETE /api/employees/:id/access`.

У сотрудника нет доступа к административным API и данным других работников. Если анкета была одобрена, карточка создаётся без учётной записи: руководитель отдельно выдаёт доступ после проверки данных.

## Самостоятельное заполнение анкет сотрудниками

- В административном интерфейсе откройте раздел «Приглашения» или кнопку «Пригласить сотрудников» в разделе «Сотрудники».
- Выберите филиал и срок действия ссылки (7–90 дней), создайте приглашение и скопируйте ссылку.
- Отправьте одну ссылку сотрудникам этого филиала. Ссылка многоразовая: каждый сотрудник отправляет отдельную анкету.
- Сотрудник открывает `/anketa/<токен>` на телефоне или компьютере и заполняет ФИО, телефон, дату рождения, должность, дату начала работы и комментарий.
- Анкета появляется в разделе «Анкеты» со статусом «На проверке». Руководитель может принять или отклонить её.
- При принятии создаётся карточка сотрудника в выбранном филиале. Учётная запись автоматически не создаётся: после принятия анкеты руководитель отдельно выдаёт доступ в разделе «Сотрудники».
- Ссылку можно отключить в разделе «Приглашения». Срок действия ограничен выбранным периодом.

**Безопасность:** анкеты сотрудников доступны публично только по секретной ссылке-приглашению. Административные API требуют авторизации руководителя. Ограничение частоты отправки публичных анкет и публикация политики обработки персональных данных остаются отдельными задачами перед полноценным промышленным использованием.


## Активация аккаунта сотрудника (v1.3.3)

1. Руководитель отправляет ссылку на анкету.
2. Сотрудник заполняет и отправляет анкету; аккаунт и доступ в кабинет на этом этапе не создаются.
3. Руководитель проверяет анкету и одобряет её в разделе «Анкеты».
4. После одобрения создаётся карточка сотрудника и одноразовая ссылка активации сроком на 72 часа. Руководитель передаёт ссылку сотруднику.
5. Сотрудник самостоятельно задаёт уникальный логин и пароль на странице `/activate/:token`. Пароль сохраняется только в виде хеша. Ссылка удаляется после успешной активации.

Для добавления таблицы `EmployeeActivation` при следующем запуске Railway выполнит обычный `prisma db push` без сброса существующих данных. Администратор больше не задаёт логин и пароль через панель сотрудников.

## Версия 1.6.0 — Backblaze B2 для фото и видео отчётов

Медиафайлы отчётов загружаются напрямую из браузера в закрытый Backblaze B2 bucket по временным подписанным S3 URL. Сервер Railway выдаёт URL после проверки сессии сотрудника и принадлежности задания; секретные ключи B2 остаются только на сервере. PostgreSQL хранит координаты и метаданные/ключи объектов, а не Base64-файлы. В админской панели выдаются временные ссылки на просмотр (1 час). Старые отчёты с Base64-вложениями продолжают отображаться.

Добавьте в Railway Variables пять параметров: `B2_KEY_ID`, `B2_APPLICATION_KEY`, `B2_BUCKET_NAME`, `B2_ENDPOINT`, `B2_REGION`. Для текущего bucket используйте имя `parkrate`, endpoint `https://s3.eu-central-003.backblazeb2.com`, region `eu-central-003`. Ключу B2 достаточно доступа к этому bucket на чтение и запись.

**CORS обязательно:** в настройках bucket добавьте правило из `docs/backblaze-cors.json`. Если приложение открывается по другому домену, добавьте его точный HTTPS origin в `allowedOrigins`. Операции PUT из браузера иначе будут заблокированы браузером. Bucket должен оставаться Private.

Для установки зависимостей выполните `npm install` (Railway обычно выполняет это при сборке), затем задеплойте приложение. Проверка отчёта: загрузить фото и видео из кабинета сотрудника, убедиться, что объекты появились в bucket `parkrate`, затем открыть раздел «Отчёты» в админке и проверить просмотр вложений. Максимальное количество и суммарный размер файлов приложением не ограничиваются; остаются физические лимиты Backblaze, браузера и сети.
